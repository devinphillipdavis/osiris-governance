## 2. Deterministic Fail-Closed Security & Command Governance

### Necessity of Deterministic Interposition
Unconstrained execution of speculative AI outputs introduces catastrophic vectors into system shells, including non-deterministic command hallucination, unverified file tree modification, arbitrary subprocess execution, and credential exfiltration. To insulate host operating system kernels from speculative reasoning engines, OSIRIS enforces a zero-trust, fail-closed interposition layer. Speculative models are strictly denied raw shell access; every proposed command payload must traverse a deterministic multi-stage interposition pipeline prior to execution.

### The 7-Layer Command Interposition Layer (CIL) Pipeline

```
[Raw Agent Directive / Proposed System Call]
                     │
                     ▼
         [L0: Syntax Sanity Check]          ---> (Fail: Malformed Input / Rejection)
                     │
                     ▼
       [L1: Intent Classification]          ---> (Classify: READ / WRITE / DESTRUCTIVE)
                     │
                     ▼
          [L2: Context Binding]             ---> (Fail: Target Out-of-Bounds)
                     │
                     ▼
           [L3: Risk Scoring]               ---> (Evaluate: SAFE to CRITICAL)
                     │
                     ▼
       [L4: Enhancement Synthesis]          ---> (Inject Resource Ceilings & Logging)
                     │
                     ▼
        [L5: Deterministic Rewrite]         ---> (e.g., rm -rf -> trash-put)
                     │
                     ▼
       [L6: Execution & Telemetry]          ---> (Isolated Subprocess + Ledger Commit)
```

1. **L0: Syntax Sanity Check:** Validates input structure against character encoding limits, bracket balance, and payload length constraints to reject malformed inputs immediately.
2. **L1: Intent Classification:** Parses payload structure to categorize the underlying action into explicit intent classes (`READ`, `WRITE`, `DESTRUCTIVE`, `SYSTEM_MUTATION`).
3. **L2: Context Binding:** Binds proposed operations to current workspace paths, active role permissions, and environment variable trees, rejecting out-of-scope targets.
4. **L3: Risk Scoring:** Evaluates parameter vectors against a risk matrix, assigning quantitative scores ranging from SAFE to CRITICAL.
5. **L4: Enhancement Synthesis:** Injects mandatory safety flags, resource constraints (CPU limits, memory caps, wall-clock timeouts), and diagnostic wrappers into candidate commands.
6. **L5: Deterministic Rewrite:** Modifies hazardous shell invocations into safe equivalents according to hardcoded policy tables (e.g., deterministically mapping destructive file removals like `rm` to the safe quarantine utility `trash-put`).
7. **L6: Execution & Telemetry Capture:** Dispatches the rewritten payload to an isolated subprocess daemon, capturing standard output, error streams, duration, and exit codes for immutable ledger logging.

### Code-Level AST Policy & Proposal Firewalls
Code proposals generated by LLMs undergo static source analysis via dedicated inspection modules (`extract_code`, `validate_ast`, `ast_verify.py`). Payload parsing relies strictly on Python's static Abstract Syntax Tree parser (`ast.parse`). Dynamic code execution primitives—specifically `exec()`, `eval()`, and `compile()`—are explicitly forbidden and blocked at the parser level.

AST verification rules are enforced via hard allowlists and denylists:

| Parameter / Policy Category | Enforcement Rule & Banned Construct |
| :--- | :--- |
| **Parsing Primitive** | Pure static analysis via `ast.parse`. Dynamic execution functions (`exec`, `eval`, `compile`) are strictly banned. |
| **Import Allowlist (`_ALLOWED_IMPORTS`)** | `['math', 'json', 're', 'hashlib', 'pathlib', 'typing', 'dataclasses', 'osiris']`. All unlisted modules are denied. |
| **Forbidden AST Nodes (`_FORBIDDEN_NODES`)** | `Exec`, `Eval`, `Global`, `Nonlocal`, `ImportFrom(os, sys, subprocess)`. Presence triggers immediate `SyntaxError`. |
| **Forbidden Function Calls (`_FORBIDDEN_CALLS`)** | `exec`, `eval`, `compile`, `open`, `system`, `popen`, `subprocess.run`, `getattr`. |
| **FileSystem & Network Boundary** | Direct file I/O and un-sandboxed socket creation are barred within proposal execution scopes. |
